## Q1. Mindcraft / MineCollab：課題、エージェント数、成功率、通信がボトルネックになるという知見

### Takeaway
MineCollabには料理・クラフト・建築の3領域があり、2〜5体のエージェントで評価されている。最も成績のよいモデル（claude-3.5-sonnet）でも建築の成功率は0.36。著者らは、詳細な計画を言葉で伝え合わせると成績が15%以上落ちること、エージェント数が増えると成績が急に下がることを示し、エージェント同士の会話が主なボトルネックだと結論している。

### Cited Findings
- 論文名は "Collaborating Action by Action: A Multi-agent LLM Framework for Embodied Reasoning"。著者はIsadora White、Kolby Nottinghamほか（UC San Diego、Latitude Gamesなど）。arXiv:2504.17950v1、2025-04-24投稿。プロジェクトサイトは https://mindcraft-minecollab.github.io/ — [arXiv](https://arxiv.org/html/2504.17950)
- 3つの領域：(1) 料理（ケーキ・パン・シチューなど。各エージェントがレシピの一部しか持たない "Hell's Kitchen" 版もある）、(2) クラフト（本棚やコンパスなど。材料が分けて配られ、一部のレシピは使えないようにしてある）、(3) 建築（ブループリントから建物を建てる。各エージェントは材料と道具の一部しか持たないので、1体だけでは完成できない） — [arXiv](https://arxiv.org/html/2504.17950)
- 建築のブループリントは手続き的に自動生成される。名前は複雑さのパラメータ（材料・部屋・窓・カーペット・バリエーション。それぞれレベル0〜2）で付けられる。採点は、建てた物とブループリントの「編集距離」をもとにした一致度で、平均スコアを報告する — [arXiv](https://arxiv.org/html/2504.17950)
- 建築の標準設定はエージェント2体、制限時間10分＋部屋の複雑さ1段階ごとに5分 — [arXiv](https://arxiv.org/html/2504.17950)
- 課題は2〜5体向けに作られている。料理とクラフトはこの範囲で人数を変えて試したが、3体以上での建築は、商用APIの費用が予算を超えるため実施していない — [arXiv](https://arxiv.org/html/2504.17950)
- 成功率（論文のTable 3）：
  - クラフト：gpt-4o 0.17、claude-3.5-sonnet 0.47、llama3.3-70b 0.16、llama3-8b-instruct 0.00、llama3-8b-sft 0.28
  - 料理：0.40 / 0.64 / 0.36 / 0.01 / 0.18
  - 建築：0.31 / 0.36 / 0.19 / 0.00 / 0.20
  - llama3-8bを追加学習（SFT）すると料理が0.01から0.18に上がり、建築では70Bモデルと同程度になった — [arXiv](https://arxiv.org/html/2504.17950)
- 通信がボトルネックだという根拠：
  - 段階的な詳しい計画を言葉で伝えることを必須にすると、クラフトと料理で成績が15%以上下がった（論文のFigure 3c–d）
  - 料理とクラフトでは、2体から5体に増やすと成績が「最大90%程度から30%未満」へ急落した
  - 建築では、ブループリントが複雑になるとllama3.3-70bとgpt-4oで約10%下がった — [arXiv](https://arxiv.org/html/2504.17950)
- 会話の仕組み：エージェントは `!startConversation` と `!endConversation` で会話を始めたり終えたりする。一度に会話できるのは2体だけで、3体以上いるときは会話の相手を切り替える。行動中は会話マネージャーが対話を一時停止し、メッセージが行動を中断しないようにしている — [arXiv](https://arxiv.org/html/2504.17950)
- 付録の失敗例：
  - 建築：1体が石の層を置いたあと、他のエージェントがそれを完全に壊してしまった
  - 料理：AndyはサトウキビをJillが持っていると思っていたが、実際にはBobが持っていた。Jillに頼んでも「持っていない」と返され、64ブロック→128ブロックと探しても見つからず、スコア0で終わった。ログには入れ子になった `startConversation` と「すでにJill_0と会話中」というシステムメッセージが残っていた — [arXiv（付録部分）](https://arxiv.org/html/2504.17950)
- 本文が挙げる失敗パターン：同じ料理を2体が作る重複作業、限られた材料の取り合い、共用かまどをめぐる衝突、計画の読み違い、資源を渡さない、目標に関係なく資源を渡す、計画をもらいに行かない／もらった計画を実行しない — [arXiv](https://arxiv.org/html/2504.17950)
- 著者が書いている限界：視覚入力はきちんと評価していない。結果は固定した版のmindcraftで出したもので、現行版とは違う可能性がある。3体以上での建築は費用の都合で試していない。プロンプトの工夫と模倣学習だけでは足りず、より高度な手法が必要 — [arXiv](https://arxiv.org/html/2504.17950)
- GitHubの現状（README）：MITライセンス。Minecraft Java Edition はv1.21.11まで対応（推奨はv1.21.6）。それ以外の版はViaProxyを試すよう書かれている。Node.jsはv18かv20 LTSを推奨（v24以上はネイティブ依存で問題が出る可能性）。複数プロファイルを同時に起動できる（例：`--profiles ./profiles/andy.json ./profiles/jill.json`）。課題はJSONで定義し、`target`、`number_of_target`、`timeout` などのフィールドを持つ。「コード実行を有効にしたまま公開サーバーにつながないこと」と警告しており、コード実行（`allow_insecure_coding`）は標準では無効。commit数は1,673だが、最終リリース日や最終コミット日はページから読み取れなかった — [GitHub](https://github.com/mindcraft-bots/mindcraft)

### Inferences
- （解釈）Mindcraftは「LLMに会話で役割分担させる」設計で、論文の結果はまさにその部分が弱いことを示している。Liz Atlasの方針（決定的なコードのコーディネーターが作業を割り当て、LLMは例外のときだけ監督役として呼ぶ）は、この知見と合っている。
- （解釈）「他のエージェントが置いたブロックを壊す」失敗は、ブロックの担当範囲が排他的に決まっていないと起きる。座標ごとの担当をコーディネーターが一意に決める設計を、この失敗例は後押ししている。
- （解釈）READMEの対応版はv1.21.11まで。Minecraft 26.1.2で動くかは確認できなかった。Liz AtlasはMineflayer 4.39を直接使うので、Mindcraftの版対応はそのまま参考にはならない。

### Gaps
- 建築採点の編集距離の正確な定義（ブロックの種類違いと位置違いの重み、回転を許すかなど）は、付録の取得範囲に入っておらず確認できなかった。
- 「90%から30%未満」は要約ツールが本文から取り出した表現で、どの課題・どのモデルの数値かを図そのもので確かめられていない。
- 要約が「claude-3.5-sonnetでも建築の成功率は0.4に届かない」という趣旨の文を崩れた形で返したため、その文は採用せず表の数値だけを載せた。

## Q2. VillagerBench / VillagerAgent：タスク分解グラフ（DAG）、建築協力タスク、結果と限界

### Takeaway
VillagerAgentは、中央の「タスク分解器」がLLMで依存関係のグラフ（DAG：一方向に流れて循環しないグラフ）を作り、「エージェント制御器」が実行可能になったサブタスクを各エージェントに割り振る、中央集権型の構成。建築課題の完成度は、GPT-4・2体で平均36.45、3体で52.17。エージェント数を増やすと中くらいの人数で頭打ちになり、8体では下がった。

### Cited Findings
- 論文は "VillagerAgent: A Graph-Based Multi-Agent Framework for Coordinating Complex Task Dependencies in Minecraft"。著者はYubo Dongほか（浙江大学 ReLER）。arXiv:2406.05720v1、2024-06-09。Mineflayerの上に作られている — [arXiv](https://arxiv.org/html/2406.05720)
- VillagerBenchの3課題：(1) 建築協力（テキストのブループリントがブロックの位置と向きを指定し、エージェントが分担して建てる。空間的な依存関係を試す）、(2) Farm-to-Table料理（ケーキとウサギシチュー。因果的な依存関係を試す）、(3) 脱出ゲーム（感圧板を同時に踏むなど。時間的な同期を試す） — [arXiv](https://arxiv.org/html/2406.05720)
- 建築の評価指標：
  - 完成度C＝正しく置けたブロック数÷ブループリントのブロック数（エージェントは材料を自分で採掘しなくてよい設定）
  - View Hit Rate（VHR）＝いくつかの視点から見た、完成形と目標形のIoU（重なりの割合）の平均
  - 依存の複雑さD＝設置経路・高さ・地面の高さ・掘る量から計算
  - 効率E＝時間あたりの達成度
  - 均衡B＝エージェント間で稼働時間がどれだけ均等か — [arXiv](https://arxiv.org/html/2406.05720)
- 仕組み：
  - タスク分解器は毎ラウンド、ゼロショットのchain-of-thought（例示なしで段階的に考えさせるプロンプト）でサブタスクのDAGをJSONで出力する。辺A→Bは「AがBより先」を意味し、直接つながっていないノードは並行して実行できる。前提のサブタスクがすべて成功したノードが「実行可能」になる
  - エージェント制御器は、実行可能なタスクとエージェントの組み合わせをLLMにJSONで出させ、割り当てたエージェントを同時に動かす
  - 状態マネージャーは、行動履歴から各エージェントの要約と、タスクに関係する環境の状態を更新する
  - 実行役の各エージェントはReAct（考える→行動する→結果を見る、を繰り返す方式）で最大6回または120秒動き、その後に振り返りを書く — [arXiv](https://arxiv.org/html/2406.05720)
- 建築の結果（Table 1。平均スコア / VHR / E / B）：Gemini-Pro 8.12 / 13.83 / 0.76 / 63.74、GLM-4 23.16 / 29.36 / 2.37 / 81.12、GPT-4-1106 36.45 / 49.05 / 3.88 / 95.38、GPT-4・3体 52.17 / 61.02 / 6.26 / 89.83 — [arXiv](https://arxiv.org/html/2406.05720)
- エージェント数を変えた実験（Table 6、建築）：
  - Task 64：1体 35.25、2体 41.67、4体 46.67、8体 30.21
  - Task 0：1・2・4体では100、8体で66.63
  - 著者は「中くらいの人数でピークになる」と説明している — [arXiv](https://arxiv.org/html/2406.05720)
- AgentVerse（LLM同士の議論で動く比較対象）との比較（Farm-to-Table、平均スコア）：AgentVerse（GPT-4）29.75、VillagerAgent（GPT-4・2体）73.75、（GPT-4・3体）85.26。失敗率はVillagerAgent 18.2%、AgentVerse 44.4%。トークン費用は1.79対10.30（ただし1行動あたりのトークンは126対107でVillagerAgentの方が多い）。AgentVerseの失敗例として、議論の中で作り話の「チェストを調べた」結果がそのまま実行に持ち込まれたことが挙がっている — [arXiv](https://arxiv.org/html/2406.05720)
- 能力が同じエージェントは56.67、能力が違うエージェントは36.67（Table 2、Farm-to-Table task 99）。能力が違うと、互いの作業待ちで詰まりやすい — [arXiv](https://arxiv.org/html/2406.05720)
- 著者が書いている限界：全体の達成率が低い（APIの範囲が広く、能力差の扱いが難しいため）。8体を超えると性能が落ちる（文脈が長くなる、タスクグラフを作るのが難しくなる、資源の取り合い、が原因として挙がっている）。現実に使うには、状況の変化、エージェントの故障、LLM出力の解釈しやすさが課題 — [arXiv](https://arxiv.org/html/2406.05720)
- 衝突を解決する専用の仕組みは書かれていない。中央の分解器・制御器と、DAGによる順序付けで衝突を避けている — [arXiv](https://arxiv.org/html/2406.05720)

### Inferences
- （解釈）「中央がDAGを作り、前提が終わったものだけを空いているエージェントに割り当てる」という骨組みは、Liz Atlasの決定的コーディネーターと同じ形をしている。違いはDAGを作るのがLLMかコードかで、litematicから層や区画ごとの依存関係（下の層が先、など）をコードで作れば、論文で分解に失敗していた部分をなくせる。
- （解釈）8体で成績が落ちた理由に「LLMの文脈が長くなる」「グラフ生成が難しくなる」が挙がっている。割り当てをLLMにやらせなければ、この2つは原理的に起きない。「資源の取り合い」だけは残るので、共用チェストや作業範囲の予約を別に設計する必要がある。

### Gaps
- 建築課題の制限時間と、1課題あたりのブロック数の分布は、取得した要約からは確認できなかった。
- AgentVerseの表の行は値が1つ足りず、平均スコア以外の指標の対応がはっきりしない（要約ツールが指摘）。

## Q3. TeamCraft、MineLand、Project Sid、S-Agentsなど：人数、構成（中央計画か分散か）、うまくいったこと、人数が増えて壊れたこと

### Takeaway
TeamCraftでは、全員の観測を見て全員の行動を出す「中央集権型」の方が分散型より明らかに成績がよく、エージェント同士がぶつかる率も低かった。4体にすると4体目を放置する失敗が出た。Project Sidは最大500体（1000体超はサーバー負荷で失敗）を数時間動かしたが、目的は社会のシミュレーションで、共同建築はできていないと著者自身が書いている。S-Agentsは「リーダー1体＋作業役」の木構造が、全員が対等なグラフ構造より速かった。

### Cited Findings
**TeamCraft**（arXiv:2412.05255v1、2024-12-06、UCLA・Amazon。ライセンスCC BY-NC-ND 4.0）
- 4課題：建築（ブループリントから建てる）、整地（範囲内のブロックをすべて撤去する）、農業、精錬 — [arXiv](https://arxiv.org/html/2412.05255)
- 建築の目標の与え方：上・左・前の3方向から見た正投影図と、言葉の指示の組み合わせ。評価は3つ。サブゴール成功率（置けたブロックの割合など）、タスク成功率（全サブゴールを達成したケースの割合）、冗長率（エージェント間の衝突回数÷全行動数。低いほどよい） — [arXiv](https://arxiv.org/html/2412.05255)
- 学習は1課題あたり2〜3体、汎化テストは4体。中央集権型は全員の観測を見て全員の行動を出す。分散型は自分の一人称視点とチームの初期インベントリだけを見る。低レベルの動作はMineflayerを「正解を出す制御器」として使っている — [arXiv](https://arxiv.org/html/2412.05255)
- TeamCraft-VLA-7B の成績（タスク成功率、かっこ内はサブゴール成功率）：
  - 建築：中央・テスト 0.42 (0.81)、分散・テスト 0.00 (0.38)、中央・4体 0.02 (0.57)
  - 整地：0.64 (0.91) / 0.20 (0.68) / 0.36 (0.81)
  - 農業：0.36 (0.63) / 0.00 (0.09) / 0.38 (0.68)
  - 精錬：0.24 (0.28) / 0.16 (0.29) / 0.06 (0.13) — [arXiv](https://arxiv.org/html/2412.05255)
- 冗長率は中央集権型7Bが平均0.01、分散型が0.15、分散型の4体テストで0.24 — [arXiv](https://arxiv.org/html/2412.05255)
- GPT-4o（例を1つだけ見せる方式）は「ほぼすべてのテストで失敗」し、タスク成功率は建築・整地・農業が0.00、精錬が0.02。空間推論の誤りとして、(8,0,8)に置くべきレンガを(7,0,9)に置いた例が挙がっている — [arXiv](https://arxiv.org/html/2412.05255)
- 4体にすると4体目を無視して2〜3体だけに仕事を割り振り、建物が完成しないことが多かった — [arXiv](https://arxiv.org/html/2412.05255)
- 著者が書いている限界：低レベル制御をMineflayerに頼っている。デモデータが手続き生成で人間のプレイではない。分散型は明示的な言葉のやり取りをしない（将来の課題）。人間のプレイヤーはまだ入っていない — [arXiv](https://arxiv.org/html/2412.05255)

**MineLand**（arXiv:2403.19267v2、2024-05-23、北京交通大学）
- 要旨では64体以上に対応とうたう。本文では画面表示ありで約32体、画面なしなら最大128体。付録には100体の戦闘シナリオがある。テストに使ったのはi5-12400Fとメモリ64GBの一般的なデスクトップPC。8体のときのCPU使用量はMalmo比で約35.6%、メモリは約38.0% — [arXiv](https://arxiv.org/html/2403.19267)
- エージェントには制限付きの感覚（距離による減衰や遮蔽のある視覚・聴覚・触覚）と、体力・空腹・酸素といった身体的な欲求がある。課題は計6,053個（要旨では「6000以上」）で、建築の課題は13個 — [arXiv](https://arxiv.org/html/2403.19267)
- 道具の解放に必要な反復回数（木/石/鉄、1体あたり）：単独 7/10/25、協力 13/20/49、競争 6/10/27。本文は「協力で1体あたりの負担が20%減る」と書くが、表では協力の方が反復回数が多く、両者は食い違っている（要約ツールの指摘を自分でも確認した） — [arXiv](https://arxiv.org/html/2403.19267)
- 建築の失敗：高い建物に必要な足場などの補助構造を計画できない。細かい精度を出すためのAPIがない。13体で演じた「ロミオとジュリエット」の評価は0.09/0.20/1と低かった — [arXiv](https://arxiv.org/html/2403.19267)

**Project Sid**（Altera、arXiv:2411.00114v1、2024-10-31、予備的な技術報告）
- PIANO構成：記憶・目標生成・会話・スキル実行などのモジュールが、共通の状態を読み書きしながら並行して動く。「認知コントローラー」が上位の決定をして会話モジュールに伝え、発言と行動が食い違わないようにする。PIANOの正式名は要旨と2章で表記が違う — [arXiv](https://arxiv.org/html/2411.00114)
- 規模：50体で4時間以上（ゲーム内で約12日）。役割分化の実験は30体×20分。税のルールの実験は29体×1200秒。文化の伝播の実験は500体×9000秒。1000体を超える実行は、Minecraftサーバーの計算量の限界を超え、エージェントがときどき反応しなくなった — [arXiv](https://arxiv.org/html/2411.00114)
- 自然に生まれた役割：農民・鉱夫・技術者・衛兵など。社会モジュールを外すと役割が安定せず、全員が同じような役になった。単独エージェントは30分で平均17種類のアイテムを集め、4時間では全約1000種のうち約320種で頭打ちになった — [arXiv](https://arxiv.org/html/2411.00114)
- 人数に関わる問題：集団になると作り話や誤解が増幅される。社会が大きくなると1対1の会話は「非効率で遅く、情報が欠ける」。小さな作り話の割合でも、やり取りを重ねると積み重なる — [arXiv](https://arxiv.org/html/2411.00114)
- 著者が書いている限界：視覚と空間推論がないため、移動と**共同建築**が制限される。古いベースモデルではGPT-4oと同じ進み方にならない — [arXiv](https://arxiv.org/html/2411.00114)

**S-Agents**（arXiv:2402.04578v4、2024-09-13、復旦大学）

- 本文は「妨げない協調はラウンド制より6.25倍速い」と書くが、本文の数値（29.0分と4.0分）から割ると約7.25倍になり、表の列の見出しにも誤りがありそうだ（要約ツールが計算・指摘したもので、自分では原表を見ていない） — [arXiv](https://arxiv.org/html/2402.04578)
- 避難小屋の建築は、図で定性的に示しているだけで、数値の評価はない。リーダーにはGPT-4、他はGPT-3.5を使い、Voyagerのスキルライブラリを再利用している — [arXiv](https://arxiv.org/html/2402.04578)

**2025〜2026年の関連研究（要旨のみ、または未読）**
- Gated Coordination（arXiv:2604.18975、2026-04-21）：長期の建築課題が対象。自分だけの実行状態と、共有する調整用の状態を分けて持つ。システムが確認した結果だけを記憶する。区画をまたぐ通信は、重要度・自分で立て直すコスト・後続への影響を比べて「必要なときだけ」行う。要旨では、通信を密にする方式や計画を固定した方式より、ブループリントの完成品質が高いと主張している。数値と人数は要旨に書かれていない — [arXiv](https://arxiv.org/abs/2604.18975)
- TickingCollab（arXiv:2606.15684、2026-06-14）：時間の制約が厳しく、協力が必須の課題のベンチマーク。要旨では、LLMは状況が変わる環境で失敗しやすく、全部を知っているオラクル（正解を知る仮想の基準）に大きく及ばないと述べ、原因に応答の遅さと部分観測を挙げている。人数と数値は要旨にない — [arXiv](https://arxiv.org/abs/2606.15684)
- CraftUtopia（ACM DL、2025）：1枚の2D画像から3D建築を作るマルチエージェントシステム。検索結果の抜粋によると、要旨は既存研究の弱点として「建築の成功率が低い」「決まったテンプレートに頼る」「人数が増えると拡張しにくい」を挙げている。本文は403エラーで読めなかった — [ACM DL](https://dl.acm.org/doi/10.65109/PUIJ7087)

### Inferences

- （解釈）「4体目を放置する」「8体で性能が落ちる」「1000体でサーバーが限界」はどれも、LLMや1台のサーバーが人数に追いつかない問題。Liz Atlasの10〜20体では、割り当てをコードにするとLLM側の問題は消えるが、サーバー（MineflayerのBot 1体ごとに1つの接続とメモリ）の負荷は別に測る必要がある。

## Q4. 共同建築研究（Minecraft Collaborative Building Task 2019、IGLU）：目標の構造物をどう記述し、完成物をどう比べるか

### Takeaway
どちらの系統も、目標は「小さな格子の中の色付きブロック」（11×9×11、6色）で、人間の設計者（Architect）が言葉で建築者（Builder）に指示する。比較は、ブロック単位の一致（F1スコア）で行う。後継研究では、位置ずれと90度回転を許す「よりフェアなF1」も提案されている。

### Cited Findings
- ACL 2019 "Collaborative Dialogue in Minecraft"（Narayan-Chen, Jayannavar, Hockenmaier）：Architectは目標の構造物を見ることができ、チャットでBuilderに指示する。Architectは様子を見られるがブロックは置けない。データセットはMinecraft Dialogue Corpus（会話とゲームログ509件）。本文のPDFは取り出せず、評価指標の詳細は読めていない — [ACL Anthology](https://aclanthology.org/P19-1537/)
- 後継研究のBAP v2（arXiv:2501.10836v3、2025-09-23）が説明する設定：建築範囲は11×9×11の格子（X・Zは−5〜+5、Yは1〜9）。色は赤・橙・黄・緑・青・紫の6色。行動の数は7,623（1マスごとに6色の設置＋撤去の7通り）。ブロックは地面（y=1）か既存のブロックの隣にしか置けない。Builderの移動はモデル化していない — [arXiv](https://arxiv.org/html/2501.10836v3)
- 従来の厳密なF1：行動を（種類, 色, マス）の組で表し、置いてから壊した足場のような打ち消し合う行動を除いた「正味の行動集合」で比べる。種類・色・マスがすべて一致した行動だけを正解とし、適合率と再現率の調和平均を全体で集計する（マイクロ平均） — [arXiv](https://arxiv.org/html/2501.10836v3)
- よりフェアなF1：何もない盤面で正しい解釈が複数ありうる問題では、予測した構造物を水平方向の平行移動と縦軸まわりの90度回転で参照解に最もよく合わせてから、厳密なF1を計算する — [arXiv](https://arxiv.org/html/2501.10836v3)
- 補助の指標として、種類F1・色F1・位置F1・形F1がある。GRUの基準モデルは種類65.2・色62.4だったが位置は27.7しかなく、著者は空間推論が主なボトルネックだと結論している。新しいモデルLlama-CRAFTSのF1は53.0（従来の最高より約6ポイント上） — [arXiv](https://arxiv.org/html/2501.10836v3)
- IGLU 2022（arXiv:2205.13771）：建築範囲は11×11×9、6色。強化学習用の行動は14種類＋カメラ操作。目標はArchitectの会話データから作った3Dのボクセル格子（立体のマス目）。評価のF1は、最終ステップの建築範囲と目標との重なりから計算する（位置合わせをするかは明記されていない）。一方、学習用の報酬は位置合わせを問わない形で、4方向の回転と平行移動の中で最も重なる値を使い、その増分を報酬にする — [ar5iv](https://ar5iv.labs.arxiv.org/html/2205.13771)
- IGLU 2022の基準モデル：10億ステップ（GPU1台で約15時間）学習し、部分課題はほぼ90%、全体の課題は25%解けた。著者は課題は「まだ解決にほど遠い」と書く。基準モデルは1エピソードでブロック1個の追加か撤去に限っており、これは課題を大きく単純化していると著者自身が認めている — [ar5iv](https://ar5iv.labs.arxiv.org/html/2205.13771)
- IGLU 2021年版は評価指標を時間の中での最大値で取っていたため特定の行動に偏りが出た。2022年版では最終ステップの値にした、と検索結果の抜粋にある（本文では未確認） — [検索結果で見つけたPDF](https://arxiv.org/pdf/2205.13771)

### Inferences
- （解釈）この系統の「目標の構造物」と「完成物」を同じ座標の格子で比べる方法は、litematicにそのまま当てはまる。litematicは座標ごとのブロック状態の一覧なので、実際のワールドから同じ範囲を読み取り、座標ごとに「正しい／違うブロック／欠けている／余分」を数えれば進捗が出せる。Liz Atlasでは置く場所が固定されているので、位置合わせ（平行移動・回転）は不要で、厳密な一致で十分と考えられる。
- （解釈）ブロックの向きなどの状態（階段の向き、ハーフブロックの上下など）は、これらの研究では扱っていない（色付きブロックだけ）。litematicの比較では、ブロックの状態まで含めるかどうかを自分で決める必要がある。

### Gaps
- 2019年のACL論文本文（評価方法と数値）は読めていない。
- IGLU 2021・2022のコンペで優勝したチームの成績は、読んだ範囲には載っていなかった。

## Q5. 全作品を通して：領域やサブタスクの割り当て、ブロック・通り道・共有資源の衝突の扱い、10体以上で1つの物理作業を何時間も続けた証拠

### Takeaway
割り当ての方法は、LLMの会話で決める（Mindcraft）、中央のLLMがDAGを作って割り当てる（VillagerAgent）、リーダー役のLLMが分ける（S-Agents）、中央のモデルが全員の行動を出す（TeamCraft）に分かれる。ブロック・通り道・共有資源の衝突を専用の仕組みで解決している研究は見つからなかった。10体以上が1つの物理的な作業（1つの建物や1つの採掘範囲）を何時間も続けたという報告も、読んだ範囲には一つもなかった。

### Cited Findings
- Mindcraftは言葉で分担し、会話が衝突の窓口も兼ねる。建築では他者が置いたブロックを壊し、料理では材料や共用かまどを取り合った — [arXiv](https://arxiv.org/html/2504.17950)
- VillagerAgentはDAGで順序を決めて衝突を避けるが、専用の衝突解決策はない。人数が増えて性能が落ちた理由の一つに「資源の取り合い」を挙げている — [arXiv](https://arxiv.org/html/2406.05720)
- TeamCraftは衝突を「冗長率」として数値で測っている（中央0.01、分散0.15、分散の4体テスト0.24） — [arXiv](https://arxiv.org/html/2412.05255)
- S-Agentsは、互いに影響する作業を別の段階に分け、独立した作業だけを並行させる。各エージェントの指示元を1体に限り、矛盾した指示を防ぐ — [arXiv](https://arxiv.org/html/2402.04578)
- Gated Coordinationは、区画をまたぐ通信を「必要なときだけ行う判断」にしている（要旨のみ） — [arXiv](https://arxiv.org/abs/2604.18975)
- 長時間・多人数の例は、Project Sidの50体×4時間以上と500体×9000秒だが、どちらも社会のシミュレーション。著者は共同建築ができていないと書いている — [arXiv](https://arxiv.org/html/2411.00114)
- 建築系の実験の規模は、Mindcraft（建築は2体、制限時間は10分＋α）、VillagerBench（建築の主実験は2体、最大8体）、TeamCraft（2〜4体）、MineLand（建築は単体中心、演劇は13体）で、どれも10体未満か短時間 — 各論文（上記URL）

### Inferences
- （解釈）Liz Atlasの「16チャンクのストリップマイニングを10〜20体で無人で何時間も続ける」は、読んだ範囲の学術研究には前例がない。研究から借りられるのは考え方（排他的な担当、依存関係の順序付け、衝突率の計測）までで、長時間の安定運用（切断・死亡・アイテムあふれからの復帰）は自分で設計して検証する必要がある。
- （解釈）採掘の担当範囲をチャンク単位で重ならないように分ければ、ブロックの取り合いは原理的に起きない。残る衝突は、通り道（拠点への帰り道）、共用チェスト、かまどなどの共有資源。予約（ロック）の仕組みをコーディネーター側に持たせるのが、TeamCraftの「中央の方が冗長率が低い」という結果と整合する。

### Gaps
- 移動経路の衝突（Bot同士が押し合う、通路が詰まる）を測った研究は見つからなかった。
- 10体以上で数時間、1つの建物や1つの採掘作業を続けた学術報告は、読んだ範囲では確認できなかった。

## Q6. LLM同士の交渉 vs 中央の決定的コーディネーター：どちらを支持する知見があるか

### Takeaway
読んだ範囲の知見はおおむね「中央で割り当てる」方を支持している。LLM同士の会話は、成績の低下（15%以上）、作り話の伝播、トークン費用の増加（約5.8倍、自分で計算）、人数が増えたときの崩れにつながっていた。ただし、比較対象はどれもLLMを使う中央方式で、「LLMを使わない決定的コード」と直接比べた研究は見つからなかった。

### Cited Findings
- 支持（中央方式）：Mindcraftで詳細な計画を言葉で伝えさせると15%以上悪化した。人数が増えると急落した。著者は通信をボトルネックと結論している — [arXiv](https://arxiv.org/html/2504.17950)
- 支持（中央方式）：VillagerAgent（中央のDAG方式）は議論型のAgentVerseに対して、失敗率18.2%対44.4%、トークン費用1.79対10.30。AgentVerseでは議論の中の作り話が実行まで伝わった — [arXiv](https://arxiv.org/html/2406.05720)
- 支持（中央方式）：TeamCraftで中央集権型は分散型より成功率が高く（建築0.42対0.00）、衝突率も低い（0.01対0.15） — [arXiv](https://arxiv.org/html/2412.05255)
- 支持（階層化・指示元の一本化）：S-Agentsで木構造（リーダー1体）は、対等なグラフ構造の押し付け合いのループを防いだ（9.3分→7.5分） — [arXiv](https://arxiv.org/html/2402.04578)
- 注意点（中央方式の弱み）：VillagerAgentは中央のLLMがタスクグラフを作るため、8体を超えると文脈の長さとグラフ生成の難しさで性能が落ちた。TeamCraftの中央モデルは4体目を放置した — [arXiv](https://arxiv.org/html/2406.05720); [arXiv](https://arxiv.org/html/2412.05255)
- 会話の効用：Project Sidでは、社会モジュール（他者とのやり取り）がないと役割が分化しなかった。ただし著者は、集団では作り話や誤解が増幅し、規模が大きくなると1対1の会話は非効率になるとも書いている — [arXiv](https://arxiv.org/html/2411.00114)
- 折衷案：Gated Coordinationは、普段は各自で処理し、必要なときだけ費用を比べて上に上げる（エスカレーションする）方式で、通信を密にする方式を上回ったと要旨で主張している（数値は未確認） — [arXiv](https://arxiv.org/abs/2604.18975)

### Inferences
- （解釈）「中央のLLMが割り当てる」方式が人数で崩れた原因（文脈の長さ、グラフ生成）は、割り当てを決定的なコードにすれば取り除ける。Liz Atlasの「決定的なコーディネーター＋例外のときだけLLM」は、VillagerAgent・TeamCraftの長所（中央管理）を残し、短所（LLMの規模の限界）を避ける構成と言える。Gated Coordinationの「普段は自分で立て直し、必要なときだけ上げる」という考え方は、LLM監督役を呼ぶ条件の設計に参考になる。
- （解釈・自分で計算した数値）VillagerAgentとAgentVerseのトークン費用の比は10.30÷1.79≒5.75倍。
- （解釈）LLMを使わない決定的コーディネーターとLLM方式を直接比べた研究は見つからなかったので、「決定的コードの方がよい」は研究から直接示されたことではなく、上の知見から推した結論である。

### Gaps
- 決定的（ルールベース）のマルチBot建築システムと、LLMマルチエージェントを同じ課題で比べた研究は見つからなかった。
- Gated Coordinationの本文（人数、数値、限界）は読めていない。
